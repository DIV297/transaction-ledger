# Assumptions & Design Decisions

## Accounts
1. **The client can't send system fields.** `POST /accounts` accepts only `name`. If `balance`, `id` or `created_at` is sent, the request is rejected with `400` instead of the field being silently ignored, so the client knows the value was not applied.
2. **Account names don't need to be unique.** Two people can share a name, and the `id` is the unique identifier.
3. **Accounts are never deleted or renamed.** The assignment doesn't ask for it, and deleting an account would leave its ledger entries without an owner.
4. **No currency field.** All accounts share one implicit currency. A real system would store a currency per account and block transfers across currencies.

## Money
5. **Amounts are stored as integers in minor units** (paise/cents) to avoid floating point errors (`0.1 + 0.2 ≠ 0.3`). The API accepts and returns major units with **at most 2 decimals**. `10.005` is rejected, not rounded.
6. **Amounts must be numbers.** `"100"` (a string) is rejected, with no implicit type coercion.
7. **There is an upper limit of 1,000,000,000 per transaction** to guard against mistakes and overflow.
8. **The balance can never go negative.** There is no overdraft. A debit equal to the full balance is allowed and leaves it at `0`.

## Transactions
9. **Only successful transactions are stored.** A rejected transaction (insufficient balance, duplicate, invalid) is not saved and does not change the balance. Every stored record is therefore a valid ledger entry, and `balance` always equals sum(credits) − sum(debits).
10. **A duplicate `reference_id` returns `409 Conflict`** and includes the original transaction in `error.details.existing_transaction`. The client can use it to reconcile a retry. The duplicate check runs before the balance check, so a retried debit gets `409` even if the balance has since dropped.
11. **A duplicate is matched on `reference_id` + `account_id` only.** If the same reference is sent again with a different amount or type, it is still treated as a duplicate and rejected. It is never treated as a new transaction.
12. **`reference_id` is case-sensitive and trimmed.** `"ABC"` and `"abc"` are different references, while `" abc "` and `"abc"` are the same.
13. **`reference_id` is supplied by the client, not generated by the backend.** It is the idempotency key, so it has to be created by the caller before the first attempt and reused on every retry. If the server generated it, each retry would get a new ID: a request whose response was lost (for example a timeout) would be applied twice, and duplicate detection could never trigger. Clients are expected to use a value from their own domain (order ID, payment ID) or a UUID. A collision on the same account is rejected with `409`, and other accounts may reuse the same value.
14. **`description` is optional.** It defaults to an empty string.
15. **Each transaction stores `balance_after`.** It is the balance right after the entry was applied, which makes statements and audits easy. This field was not in the spec but is useful in a ledger.
16. **Transactions are immutable.** No update or delete endpoints exist. At the model level, the fields are marked `immutable` and every update/delete query on the collection throws an error.

## History & pagination
17. **Results are sorted by `created_at` descending, then by `_id` descending**, so that two entries created in the same millisecond keep a stable order.
18. **Defaults are `page=1` and `limit=10`, and the maximum `limit` is 100.** Values that are not integers, zero, negative or over the limit return `400`. They are not silently clamped.
19. **Requesting a page beyond `total_pages` returns an empty list with `200`**, not an error.
20. **History for an account that doesn't exist returns `404`**, not an empty list.

## Consistency & concurrency
21. **Each balance update and its transaction insert run in one MongoDB multi-document transaction.** If either fails, both are rolled back. This requires a replica set (MongoDB Atlas provides one).
22. **The sufficient-balance check is part of the update itself** (`balance >= amount` in the update filter), not a separate read followed by a write. Concurrent debits therefore can't overdraw an account. This was tested: 10 parallel debits of 10 on a balance of 70 gave exactly 7 successes and a final balance of 0.
23. **A unique index on `(account_id, reference_id)` is the final safeguard against duplicates**, for example when the same request is sent twice at the same moment.

## Transfers (bonus)
24. **A transfer is two ledger entries**: a debit on the source and a credit on the destination. They are linked by `transfer_id` and share the transfer's `reference_id`. There is no separate transfers collection, so balances stay derivable from transactions alone.
25. **The `reference_id` must be unused on both accounts.** If either account already has it, the whole transfer is rejected with `409` and rolled back.
26. **Transferring to the same account is rejected** (`400`).

## Out of scope
- Authentication and authorization: any caller can operate on any account.
- Rate limiting, multi-currency support, and reversing or refunding a transaction (this would be done by posting a new opposite entry, never by editing).
